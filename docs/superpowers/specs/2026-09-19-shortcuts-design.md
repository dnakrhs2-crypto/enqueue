|---|---|---|

`createXml(true)` 자체는 좋은 기능입니다. 다만 “기존 기본 키를 제거했다”는 차이와 “이 기능은 앞으로도 내가 지정한 키만 쓴다”는 의도는 다릅니다. 이번에는 후자를 보장하는 **기능별 덮어쓰기 모델**을 추천합니다. [JUCE 매핑 API](https://docs.juce.com/master/classjuce_1_1KeyPressMappingSet.html)

**모델은 다음 세 층으로 나눕니다.**

- **기능 목록**: 안정적인 문자열 ID, 이름, 설명, 카테고리, 기본 키 목록, 동작 범위, 반복 허용 여부, 실행 대상.
- **사용자 설정**: 변경한 기능의 키 목록만 저장합니다.
- **현재 유효 매핑**: 기능 목록과 사용자 설정을 합치고 충돌·플랫폼 제약을 해석한 결과입니다.

예를 들어 `transport.go`, `transport.panicAll`, `cueTable.editNumber`, `waveform.addSlice`처럼 이름과 무관한 ID를 사용합니다. 현재 `Commands.h`의 숫자 ID는 연속 enum이므로, 저장 계약을 그 숫자에만 의존시키지 않습니다.

설정의 의미는 다음으로 고정합니다.

| 저장 상태 | 의미 |
|---|---|
| 해당 기능 항목 없음 | 현재 버전의 기본 키 사용 |
| 해당 기능에 키 목록 있음 | 그 목록만 사용 |
| 해당 기능에 빈 목록 있음 | 명시적으로 단축키 없음 |
| 명령별 기본값 복원 | 해당 기능의 덮어쓰기 항목 제거 |
| 전체 기본값 복원 | 모든 덮어쓰기 항목 제거 |

새 명령은 기본 키를 받습니다. 다만 그 키를 사용자가 다른 기능에 이미 지정했다면 **사용자 지정을 유지하고 새 기본 키를 비활성화하여 알립니다.** 업데이트가 기존 사용자 키를 빼앗지 않습니다.

**‘모든 단축키’의 포함 범위**

75개 명령 외에도 다음을 기능 목록에 포함합니다.

| 영역 | 포함할 키 동작 |
|---|---|
| 큐 표 | N/Q/E/W/C/O/D 편집, 그룹 접기·펼치기, 행 이동·범위 선택·페이지 이동 |
| 파형 | Shift+I/O, M, 선택 항목 삭제, 점 선택, 일반·미세 점 이동, 키보드 확대·축소 |
| 레벨 매트릭스 | 셀 이동, 무음 처리, Enter/F2 편집 시작 |
| 곡선 편집기 | 선택 점 삭제 |
| 그룹 타임라인 | 자식 선택, 프리웨이트 일반·미세 이동 |
| 기타 | JUCE 종료 명령 등 앱에 등록된 모든 명령 |

일반·미세 이동도 별도 기능으로 등록합니다. 단축키를 바꾼 뒤에도 내부에서 고정 Shift 여부로 동작을 결정하면 전체 커스터마이징이 되지 않기 때문입니다.

문자 입력, 입력창의 복사·붙여넣기, 대화상자 확인·취소, 일반적인 Tab 포커스 이동은 **표준 UI 조작**으로 유지합니다. 키보드 단축키와 별개인 마우스 조합, 플러그인 자체 단축키, OS 단축키도 이번 설정 대상에는 포함하지 않습니다.

**저장 위치·형식**

- 위치: 기존 `%APPDATA%\Enqueue\Enqueue.settings`.
- 주 키 이름: `keyboardShortcuts`.
- 직전 정상 설정: `keyboardShortcutsLastGood`.
- 값: 버전이 있는 XML.
- 프로젝트에는 명령 단축키를 저장하지 않습니다. 단축키 변경으로 프로젝트가 수정 상태가 되어서도 안 됩니다.

형식 예시는 다음과 같습니다.

```xml
<ENQUEUE_SHORTCUTS schemaVersion="1" platform="windows">
  <ACTION id="transport.go">
    <KEY key="Space"/>
    <KEY key="F13"/>
  </ACTION>
  <ACTION id="transport.panicAll">
    <KEY key="F12"/>
  </ACTION>
  <ACTION id="transport.preview"/>
</ENQUEUE_SHORTCUTS>
```

키는 안정적인 이름과 Ctrl/Alt/Shift 속성으로 저장합니다. 표시용 한국어 문자열이나 기기별 스캔코드는 저장 기준으로 사용하지 않습니다.

JUCE의 `createFromDescription()`은 알 수 없는 문자열에서도 마지막 문자 등을 키로 해석할 수 있습니다. 따라서 **`isValid()`만으로 가져온 값을 검증하지 않습니다.** 허용된 키 이름·modifier를 엄격하게 파싱한 뒤 JUCE 키로 변환합니다.

**손상·구버전 처리**

- 값이 없으면 기본값을 사용합니다.
- 지원하는 구버전은 명시적인 변환 함수를 거칩니다.
- 알 수 없는 기능 ID는 실행하지 않고 보존합니다.
- 더 최신인 스키마는 적용을 거부하고 원문을 보존합니다.
- 손상된 설정은 직전 정상 설정, 그것도 없으면 기본값으로 복구하고 알립니다.
- 손상 원문을 시작 과정에서 정상 기본값으로 조용히 덮어쓰지 않습니다.
- 가져오기 실패는 현재 매핑에 영향을 주지 않습니다.

**내보내기·가져오기는 첫 완성 범위에 포함**하는 것을 추천합니다. 다른 공연 PC로 옮기는 사용 목적과 직접 연결됩니다.

파일은 UTF-8 XML인 `*.enqueue-shortcuts.xml`로 합니다. 내부 저장은 변경분만 저장하지만, 내보내기는 **현재 해석된 전체 키 목록**을 담습니다. 가져오면 해당 기능들은 명시적인 사용자 설정이 되어 다른 버전에서도 같은 키를 재현합니다. 파일에 없는 새 기능은 기본값을 따릅니다.

가져오기는 기본적으로 현재 PC 설정을 교체하며, 적용 전에 변경·미지정·충돌 목록을 보여줍니다. 큐 핫키와 오디오 장치 설정은 이 파일에 포함하지 않습니다.

**목록 규칙**

앱의 100/110/125/150% 배율을 그대로 따르고 탭만 글씨를 축소하지 않습니다. 긴 설명은 선택 영역에서 줄바꿈합니다. 작은 화면에서는 목록 높이를 줄이고 스크롤로 접근하게 하며 하단 버튼이 화면 밖으로 나가지 않게 합니다.

**4. 충돌·우선순위 규칙**

**‘이 키의 주인’을 판단하는 함수를 하나로 둡니다.**

예를 들어 `resolveKeyOwner(key, context, profile, project)`는 다음을 반환합니다.

- 실행 대상 또는 표준 UI 처리 대상.
- 해당 범위에서 사용 가능한지.
- 사용할 수 없다면 이유.
- 같은 키를 사용하는 다른 범위·큐.
- 이벤트를 소비할지, UI에 전달할지.

설정 UI, 큐 핫키 캡처, 실제 입력 처리, 프로젝트 충돌 표시가 이 판정을 공유합니다. `Hotkeys::isReservedKey()` 같은 고정 문자 목록과 별도의 판단을 유지하지 않습니다.

**실행 우선순위**

1. 캡처 중이면 캡처만 처리.
2. 패닉 키면 패닉 전용 경로에서 한 번 처리.
3. 입력창·대화상자의 표준 조작 처리.
4. 현재 포커스에 해당하는 컴포넌트 기능 처리.
5. 해당 창에서 허용되는 앱 명령 처리.
6. 충돌 없이 활성화된 큐 핫키 처리.

패닉은 키를 소비하지 않는 별도 관찰 경로이므로, 기본 Esc는 패닉과 대화상자 취소가 함께 일어날 수 있습니다. 캡처 중에는 이 예외도 막습니다.

| 충돌 종류 | 추천 규칙 |
|---|---|
| 같은 범위의 명령↔명령 | 중복 활성화 금지. `[기존 기능에서 이 키 이동] / [취소]` 제시 |
| 같은 기능의 같은 키 | 변경 없음 |
| 서로 배타적인 컴포넌트 범위 | 허용. 예: 매트릭스 ←와 파형 ← |
| 컴포넌트 기능↔넓은 범위의 명령 | 컴포넌트 우선. 어디서 어떤 기능이 이기는지 표시하고 추가 시 알림 |
| 패닉↔다른 앱 기능 | 중복 활성화 금지. 패닉이 포커스에 따라 가려지지 않게 함 |
| 앱 기능↔큐 핫키 | 앱 기능 우선. 큐 핫키는 값을 보존한 채 비활성화 |
| 큐↔큐 | 새 지정은 거부. 파일에서 발견된 중복은 해당 중복 키를 비활성화하고 알림 |

**JUCE 자동 충돌 제거에 의존하면 안 됩니다.**

공식 API 문서는 `addKeyPress()`가 이전 명령에서 키를 제거한다고 설명하지만, 이 PC가 사용하는 JUCE 8.0.15 기반 소스의 실제 구현에는 그 제거가 없습니다. 해당 파일은 로컬 추가 패치로도 변경되지 않았습니다. 따라서 이동은 앱에서 명시적으로 기존 할당을 제거하고 새 할당을 추가하는 하나의 작업으로 처리합니다. [실제 addKeyPress 구현](/C:/Users/claude/JUCE/modules/juce_gui_basics/commands/juce_KeyPressMappingSet.cpp:65), [공식 API 설명](https://docs.juce.com/master/classjuce_1_1KeyPressMappingSet.html)

**컴포넌트 키는 ‘고정 예약 키’에서 설정 가능한 기능으로 전환합니다.**

예를 들어 N을 다른 기능에 지정했을 때 큐 표 안에서는 번호 편집이 우선이라는 사실을 표시합니다. 사용자가 N을 완전히 넘기고 싶다면 번호 편집의 N도 제거합니다.

현재 큐 표에는 `TableListBox`의 Delete·Backspace가 `deleteKeyPressed()`를 통해 큐 삭제 명령을 직접 실행하는 우회 경로가 있습니다. 이를 남기면 큐 삭제 키를 바꿔도 옛 키가 작동합니다. 기본값 목록에 실제 기존 동작을 반영하고, 처리 경로는 설정된 매핑으로 통일해야 합니다. [큐 표 삭제 경로](/C:/Users/claude/gocue/src/ui/CueTable.cpp:929)

**명령↔큐 핫키**

현재 로더는 예약 키·중복 키를 실제로 지웁니다. 이 부분은 **문법 정규화와 진단**, **현재 PC에서의 실행 가능 여부**로 분리해야 합니다. 로더가 `AppSettings`에 의존하게 만들지 않습니다. [현재 로더](/C:/Users/claude/gocue/src/model/ProjectSerializer.cpp:934)

**5. Esc·패닉 훅**

**추천은 기존 `WH_KEYBOARD`를 유지하면서 Esc 전용 훅을 ‘현재 패닉 매핑을 보는 훅’으로 바꾸는 것입니다.**

현재 Windows 훅은:

- 첫 key-down만 처리합니다.
- `VK_ESCAPE`만 봅니다.
- modifier는 검사하지 않습니다.
- 이벤트를 소비하지 않습니다.

따라서 현재는 modifier를 누른 Esc도 훅 조건에 들어갑니다. 새 설계에서는 **등록된 modifier와 정확히 일치**할 때만 패닉으로 해석합니다. 이는 명시적인 동작 변경입니다. [현재 훅](/C:/Users/claude/gocue/src/Main.cpp:20)

**매핑과 실행 경로**

- 기본 패닉 키는 Esc입니다.
- Windows에서도 설정 모델과 JUCE 표시용 매핑에는 Esc를 등록합니다.
- 키보드에 의한 실제 패닉 실행은 훅 한 곳이 담당합니다.
- 일반 단축키 라우터는 같은 키로 패닉을 다시 호출하지 않습니다.
- 메뉴·버튼은 공통 패닉 처리 함수를 호출합니다.
- F12로 바꾸면 F12가 즉시 훅 대상이 됩니다.
- Esc를 제거하면 Esc는 취소·닫기 기능만 남습니다.
- 숨겨진 ‘항상 살아 있는 Esc’는 두지 않습니다.

훅을 매번 해제·재설치하지 않고, **검증·변환이 끝난 읽기 전용 패닉 키 목록을 교체**합니다.

**KeyPress→Windows 키 변환**

문자열에서 VK를 추측하거나 모든 키에 `& 0xff`를 적용하지 않습니다.

- 문자·숫자, F1~F24, 방향·편집 키, 지원하는 넘패드는 명시적인 대응표로 변환합니다.
- OEM 문장부호는 현재 키보드 레이아웃에서 표현 가능 여부를 검사합니다.
- Ctrl/Alt/Shift 상태는 훅에서 이벤트를 관찰한 시점에 함께 기록합니다.
- modifier 판정을 비동기 콜백 실행 때 다시 하지 않습니다.
- JUCE의 확장 키 코드와 Windows `lParam`의 extended 비트를 혼동하지 않습니다.
- 패닉 등록에는 일반 캡처 성공 외에 **훅 변환 가능 여부**가 추가 조건입니다.

키보드 훅의 이전 상태·전환 비트는 반복과 key-up을 구분하는 근거가 됩니다. modifier 상태도 이벤트 처리 시점의 키 상태를 기준으로 다뤄야 합니다. [Microsoft KeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/keyboardproc), [GetKeyState](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeystate)

변환을 보장하지 못하는 키는 패닉용 등록을 거부하고 “플러그인 창에서도 동작하는 전체 정지 키로 사용할 수 없습니다”라고 표시합니다. 처음부터 F12·F13 등 지원이 명확한 키를 선택할 수 있게 합니다.

패닉에 문자나 편집 키를 지정하면 입력창에서도 작동한다는 사실을 등록 화면에 보여줍니다. 마지막 패닉 키 제거는 허용하되, “키보드로 전체 정지를 할 수 없음”을 확인받습니다. 메뉴·버튼은 유지합니다.

**Esc 취소·캡처**

평상시 훅은 계속 키를 소비하지 않습니다. Esc가 패닉 키라면 기존처럼 정지와 대화상자 취소가 함께 동작합니다.

캡처 중 Esc는 **캡처 취소만** 합니다. 훅에서 캡처 여부를 관찰한 즉시 기록해야 합니다. 비동기 실행 시점에는 캡처가 끝났다는 이유로 뒤늦게 패닉을 실행해서는 안 됩니다.

**0.5초 두 번**

- 반복 key-down은 두 번째 누름이 아닙니다.
- 두 번 판정은 개별 키가 아니라 패닉 기능 단위로 합니다.
- Esc와 F12를 모두 지정했다면 두 키를 차례로 누르는 것도 두 번입니다.
- 훅에서 기록한 발생 시각을 전달하여 메시지 처리 지연으로 판정이 달라지지 않게 합니다.
- 매핑 변경·캡처가 이전 입력을 두 번째 패닉으로 재사용하지 않게 상태를 정리합니다.

현재 `panicFromAnywhere()`에는 재생 중 경로 외에, 큐가 없는 상태에서 자체 발음하는 플러그인의 출력을 끄는 경로가 있습니다. 이 동작도 유지해야 합니다. 패닉을 무조건 `controller.panicAll()`로 치환하면 안 됩니다. [현재 전체 창 패닉 처리](/C:/Users/claude/gocue/src/ui/MainComponent.cpp:3295)

**플러그인 창과 보장 범위**

현재 훅은 **설치한 UI 스레드의 창**을 대상으로 합니다. 같은 스레드의 네이티브 플러그인 편집기가 JUCE 키 이벤트를 삼키는 경우는 이 구조로 처리합니다.

플러그인이 별도 UI 스레드나 외부 프로세스를 사용하는 경우까지 모두 잡힌다는 것은 **추정이며 현재 코드만으로 보장할 수 없습니다.** 같은 프로세스의 별도 UI 스레드가 확인되면 그 창의 스레드에도 관리되는 훅을 설치하는 확장점을 둡니다. 외부 프로세스 창 지원은 별도 범위입니다. 앱 전체를 대상으로 한 시스템 전역 훅으로 바로 확대하지는 않습니다. [SetWindowsHookEx의 스레드 범위](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)

훅 설치 실패는 사용자에게 표시하고, JUCE 창 안에서만 동작하는 단일 대체 경로로 전환합니다. 훅과 대체 경로가 동시에 활성화되면 안 됩니다.

**비Windows**

현재 CMake는 Windows 이외의 빌드를 거부합니다. 비Windows 코드는 현재 배포 동작이 아니라 향후 대비 코드입니다.

향후에는 같은 설정·충돌·반복 판정을 사용하고, JUCE 입력 라우터에서 패닉을 한 번 실행합니다. `onEscapeKey`에서 패닉을 직접 호출하는 잔여 경로는 없애야 합니다. 네이티브 플러그인 창까지 보장하려면 해당 OS의 별도 입력 어댑터가 필요합니다.

**6. 적용 시점·저장·다른 창**

**변경을 확정한 즉시 반영하되, 한 번의 변경을 하나의 작업으로 처리합니다.**

권장 순서입니다.

1. 현재 설정을 바탕으로 후보를 만듭니다.
2. 키 문법·충돌·동작 범위·훅 변환을 검증합니다.
3. 충돌 이동 등의 확인을 완료합니다.
4. 설정을 저장하고 저장 성공 여부를 확인합니다.
5. 현재 매핑, JUCE 표시용 매핑, 훅 목록을 교체합니다.
6. 메뉴·트랜스포트·설명 문구·큐 충돌 상태를 갱신합니다.

저장 실패 시 기존 매핑을 유지하고 오류를 표시합니다. “화면에는 바뀌었는데 재시작하면 되돌아감”을 정상 동작으로 만들지 않습니다.

`AppSettings`에는 저장 성공을 반환하는 전용 변경 API를 둡니다. 기존 1초 자동 저장과 종료 시 flush는 보조 경로로 유지하되, 단축키 변경은 성공 여부를 확인하는 즉시 저장 경로를 사용합니다. 저장은 캡처 확정 시 수행하고 훅 콜백이나 오디오 스레드에서 수행하지 않습니다.

**입력 경로 통합**

현재의 원시 `KeyPressMappingSet` 리스너, 큐 핫키 리스너, Space 전용 `OperationalKeys`를 독립 실행 경로로 남기지 않습니다.

새 라우터가 소유권을 결정하고:

- 기존 명령은 `ApplicationCommandManager`로 실행합니다.
- 컴포넌트 기능은 해당 컴포넌트의 등록된 실행 함수로 전달합니다.
- 큐 핫키는 기존 `CueController`로 전달합니다.
- Windows 패닉 키는 훅 경로에서 처리합니다.

키보드 실행은 `InvocationInfo::fromKeyPress`, 실제 키, down/up 정보를 보존합니다. `invokeDirectly()`로 바꿔 호출하면 GO의 키 해제 정책을 잃을 수 있습니다.

JUCE는 자식 컴포넌트가 키를 먼저 처리할 수 있으므로 **최상위 창에 리스너 하나를 추가하는 것만으로 통일했다고 보면 안 됩니다.** 자체 키 처리 컴포넌트와 포커스 입력 경로도 함께 수정합니다.

**반복·여러 GO 키**

- GO·패닉·큐 발사는 물리적인 한 번 누름당 한 번 처리합니다.
- 일반 명령도 기본적으로 반복을 억제합니다.
- 행 이동·점 이동처럼 반복이 필요한 기능만 반복을 허용합니다.
- `requireKeyUp`이 켜졌을 때는 여러 GO 키의 눌림 상태를 함께 추적합니다.
- Space와 F13을 누른 상태에서 하나만 뗐다고 전체 GO 해제 상태로 바꾸지 않습니다.
- 앱 내 창 이동과 다른 앱으로의 전환을 구분합니다.
- 포커스 복귀나 매핑 교체가 아직 누른 키를 새 누름으로 만들면 안 됩니다.

기존 더블 GO 시간 제한, 큐별 `doubleGoHotkeys`, 카트 클릭 정책은 유지합니다.

| 캡처 | GO·큐·패닉·기본 버튼이 실행되지 않음. 캡처 종료 후 반복 입력도 실행되지 않음 |
| 여러 GO 키 | 키 해제·포커스 이동·modifier 변경에도 중복 GO가 생기지 않음 |
| 훅 변환 | F13/F24·조합·넘패드·OEM 키·변환 불가 입력을 올바르게 판정함 |
| 패닉 횟수 | 첫 누름·반복·해제·두 번째 누름·다른 별칭·0.5초 경계를 구분함 |
| 패닉 단일 경로 | 훅과 JUCE 이벤트가 모두 들어와도 패닉은 한 번만 실행됨 |
| 이벤트 시점 | 캡처 종료·매핑 변경 전에 관찰한 비동기 이벤트가 뒤늦게 실행되지 않음 |
| 기능 목록 | 현재 등록된 명령과 자체 키 기능이 설정 목록에서 누락되지 않음 |

핵심 테스트는 가짜 입력 이벤트와 실행 기록으로 **“어떤 기능이 몇 번 실행됐는가”**를 검사합니다. 단순히 내부 자료구조를 그대로 비교하는 테스트에 그치지 않습니다.

**gom GUI 실측 시나리오**

1. GO에 Space를 유지하고 장치의 F13을 추가합니다. 메뉴·목록·동작을 확인하고 재시작 후 두 키 모두 확인합니다.
2. Space를 제거합니다. 메인·설명서·보조 창 어디에도 옛 Space→GO가 남지 않는지 확인합니다.
3. 캡처에서 Space·Enter·Tab·Backspace·Delete·현재 패닉 키를 누릅니다. 재생·정지·대화상자 확인이 일어나지 않아야 합니다.
4. Esc로 캡처를 취소합니다. 설정창이 함께 닫히거나 패닉이 발생하지 않아야 합니다.
5. 키를 누른 채 등록하고 계속 유지합니다. 해제 후 새로 누르기 전까지 실행되지 않아야 합니다.
6. F13/F24, Ctrl+Alt 조합, 넘패드 NumLock 켬·끔을 실제 장치로 확인합니다.
7. Space와 F13을 겹쳐 누르고 각각 해제합니다. `requireKeyUp` 켬·끔과 더블 GO 제한을 확인합니다.
8. 패닉을 Esc→F12로 바꿉니다. 메인·입력창·설정창·플러그인 편집기에서 F12를 확인합니다.
9. Esc는 취소만 하는지 확인합니다. F12 길게 누르기는 한 번, 0.5초 안 두 번은 즉시 정지여야 합니다.
10. 큐가 재생되지 않는 상태에서 자체 발음하는 플러그인의 출력도 패닉으로 차단되는지 확인합니다.
11. 명령 충돌의 취소·키 이동을 각각 확인합니다. 이동 후 이전 명령이 실행되면 실패입니다.
12. 다른 리스트·카트의 큐 핫키와 명령 키를 충돌시킵니다. 경고·비활성화·값 보존·충돌 해소 후 복구를 확인합니다.
13. N, 파형 삭제·이동, 매트릭스 편집, 곡선 삭제, 타임라인 이동을 바꾸고 옛 키가 남지 않는지 확인합니다.
14. 큐 삭제 키를 바꾼 뒤 특히 **표의 Delete·Backspace 우회 경로**를 확인합니다.
15. 입력창의 한글 조합·복사·실행 취소·Enter·Tab이 유지되는지 확인합니다.
16. 명령별·전체 기본값 복원, 다른 PC로 내보내기·가져오기, 손상 파일 가져오기 취소를 확인합니다.
17. 100/110/125/150%와 Windows DPI 변경·다중 모니터에서 목록·캡처·하단 버튼을 확인합니다.
18. 쇼 모드에서 기존 키는 허용 범위대로 동작하고 설정 변경·편집 우회는 차단되는지 확인합니다.
19. 다른 앱으로 전환했다 돌아오거나, 키를 누른 채 창을 닫았을 때 유령 입력이 생기지 않는지 확인합니다.

GUI 입력 도우미를 사용할 때도 실제 장치를 마지막에 확인해야 합니다. README에 적힌 것처럼 단순 SendKeys와 스캔코드를 사용하는 입력의 JUCE 도달 방식이 다를 수 있습니다.

**9. 구현 단계·리스크·예상 변경 파일**

**세션 1 — 기능 목록과 저장 계약**

75개 명령과 컴포넌트 자체 키를 목록화합니다. 기본값·범위·반복 정책, 안정적인 ID, 엄격한 키 파서, 저장·복구·업데이트 충돌 처리를 구현합니다.

검토 기준은 “모든 기존 동작이 목록에 있는가”, “미지정과 기본값 상속을 구별하는가”, “업데이트가 사용자 키를 바꾸지 않는가”입니다.

**세션 2 — 입력 경로와 패닉**

공통 라우터, GO 눌림 상태, Windows 패닉 어댑터, 캡처 차단 상태를 먼저 구현합니다. 기존 키로 동작을 유지하면서 중복 발화·포커스·키 해제 문제를 검증합니다.

패닉과 GO 검증을 통과하기 전에는 설정 UI 완성을 우선하지 않습니다.

**세션 3 — 공용 캡처와 단축키 탭**

기존 큐 캡처를 공용 세션으로 옮기고 검색·복수 키·추가·교체·삭제·복원·충돌 확인을 구현합니다. 저장 실패와 포커스 이동까지 점검합니다.

**세션 4 — 컴포넌트 키와 큐 핫키 통합**

큐 표·파형·매트릭스·곡선·타임라인의 고정 분기를 기능 실행으로 전환합니다. 상속된 JUCE 우회 경로도 정리합니다. 큐 핫키 로더의 삭제 정책을 보존·진단 정책으로 바꾸고 프로젝트 버전 호환을 처리합니다.

이 단계가 끝나기 전에는 “모든 단축키 커스터마이징 완료”로 보지 않습니다.

**세션 5 — 이동성과 표시**

가져오기·내보내기, 동적 메뉴·트랜스포트 표시, 설명서·README를 완성합니다. 설정 저장 후 앱 종료 없이 파일에 반영되는지도 확인합니다.

**세션 6 — 통합 리뷰와 실측**

기본 설정, 많이 수정한 설정, 구버전 프로젝트, 충돌 프로젝트로 전체 GUI 시나리오를 수행합니다. 실제 장치와 사용 중인 플러그인 편집기에서 검증합니다.

**gom에게 물어볼 것**

이번 설계를 결정하기 위해 꼭 필요한 열린 질문은 없습니다. 기본 범위는 **Enqueue가 활성화된 상태의 키 입력 장치 연동**, **복수 키 지원**, **컴포넌트 자체 키 포함**, **가져오기·내보내기 포함**, **MIDI와 OS 전역 핫키 제외**로 정했습니다.

구현 후 실측에는 실제 사용하는 장치와 플러그인 목록이 필요합니다. 이는 저장 모델이나 UI 결정을 미룰 사유가 아니라, 플러그인 창과 장치 입력의 지원 범위를 확인할 검증 자료입니다.
