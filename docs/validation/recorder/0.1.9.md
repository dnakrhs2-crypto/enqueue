## AAC/M4A 정렬 회귀 (Windows 업데이트)
- 증상: `AudioImportTests` "MP3/M4A priming, final padding, source alignment and seek: compressed source alignment" 실패(m4a rms 0.294, 03:05 통과 때는 0.0061). 03:28에 만든 0.1.8 테스트 실행 파일도 이제 같은 값으로 실패 → 빌드가 아니라 환경. Enqueue `MediaFoundationTests`도 lag −1024로 실패(ctest에 포함되어 배포 차단).
- 추적: 시프트 스캔 → 캐시가 정확히 +1024샘플 늦음. ffmpeg.exe 단독 인코드/디코드 라운드트립은 정상(rms 0.005). 임시 프로브로 MF 버퍼를 찍으니 timestamp 0(1024프레임=프라이밍) → 1024 → 2048 …: 업데이트 전에는 프라이밍과 첫 실제 프레임이 둘 다 timestamp 0으로 와서 리더가 중복을 버렸는데, 이제 MP4 소스가 편집 목록을 적용하지 않은 raw media time을 준다. MF_PD_DURATION은 여전히 편집 목록 적용 길이. Windows Update 이벤트 로그 05:03:18 KB5124008 설치 성공.
- 수정(`src/audio/MediaFoundationAudioFormat.cpp`, Enqueue·LiveMix·Tally 공용): MP4 박스를 직접 읽어 첫 오디오 트랙의 elst media_time(프라이밍)을 얻고, 열 때 첫 두 버퍼로 raw 여부를 판별(단조 = raw)해 raw면 모든 position을 −editListStart 시프트(프라이밍은 0 이전이 되어 skipUntil로 버려짐). seek는 raw 시간으로 위치 지정하되 2048 프리롤을 raw 기준으로 계산(1차 시도에서 presentation 기준으로 계산해 seek 0이 프라이밍을 건너뛰어 앞 ~1500샘플이 틀렸음: 덤프 vs ffmpeg rms 0.34 → 0.00009).
- 판별 근거를 실측이 아닌 파일 정보(elst)에 두었으므로 인코더가 2112 프라이밍을 쓰는 파일도 그대로 맞고, edit list가 없는 .aac/.wma는 종전과 같다.
- 첫 시도로 넣었던 "Recorder 가져오기 쪽에서만 readerStartSample로 건너뛰기"는 공용 리더 수정과 이중 건너뛰기가 되어 되돌렸다.

## 리뷰
- 1차(`brief_recorder_mf_review.txt`, `mf-review1-OUT.md`): "fix first" — P2 파서 필드 읽기가 박스 경계·실패를 검사하지 않음, P2 `at + size` 정수 overflow·media_time 환산 범위, P2 빈 edit·복수 edit·재생률을 단순 offset으로 처리; 프로브(첫 두 버퍼 단조 = raw)가 "편집 목록 적용 + 단조 timestamp"인 구 Windows 파일을 구분 못 한다는 주의(다만 그런 파일이 실제 있다는 근거는 없음).
- 수정(032b382): 파서 전면 재작성 — 단일 경계 검사 읽기 원시(`readBytes`, 덧셈 전 비교·정확 길이 일치), 64/32비트 size를 `limit - at`와 먼저 비교, version 0/1만, `entry_count == 1`·media_time ≥ 0·rate 1.0인 단일 edit만 인정, 환산 결과 [0, 1e9] 밖이면 0; 적용 조건에 `nativeStreamIsAac()`(GetNativeMediaType 서브타입 AAC) 추가. 프로브 방식은 유지하고 잔여 위험은 아래에 기록.
- 2차(`brief_recorder_mf_review2.txt`, `mf-review2-OUT.md`): "fix first" — 경계·크기·edit 처리·AAC 제한·4cc 비교·GetNativeMediaType 시점은 닫힘; 남은 P2 1건 = seek 산술(`target + editListStart` overflow, 100 ns 변환의 LONGLONG 범위)에 상한 검사 없음. 후속 보강 후보로 "알려진 파형의 짧은 AAC 기준 파일을 프로세스당 한 번 디코드해 환경 동작을 독립 확인"을 제안(이번 범위 밖).
- 수정(seek 범위 가드): 덧셈 전 `target <= INT64_MAX - offset` 검사, ticks를 double로 계산해 유한·0 이상·< 9.2e18(2^63 미만)일 때만 LONGLONG으로 캐스트해 SetCurrentPosition; 아니면 기존 seek 실패 경로(무음).
- 3차(`brief_recorder_mf_review3.txt`, `mf-review3-OUT.md`): "ship" — seek overflow·ticks 범위·캐스트 검사 유효, 실패 경로는 종전과 동일(같은 위치라도 seekFailed면 다음 읽기가 seekTo를 다시 시도하고 범위 밖이면 SetCurrentPosition 없이 무음), 정상 seek 산술 불변. 배포 차단 결함 없음.
